# Threat model (slice 1)

**Assets:** owner passphrase/session, approval integrity, the database (conversations, memory, drafts), future provider keys and account connections, budget.
**Actors:** remote attacker (if ever exposed), malicious web content fetched for research, malicious local web page in Luke's browser, a compromised dependency, a future prompt-injected model.
**Trust boundaries:** browser ↔ API · API ↔ worker/tools ↔ network · API ↔ future adapters (calendar, SMS, Sandra, Mac).

| Threat | Mitigation in code | Residual / next |
|---|---|---|
| Remote access to API | Binds `127.0.0.1` by default; warns otherwise; no public deployment made | TLS + reverse proxy + passkeys before any exposure |
| DNS-rebinding / hostile local page driving the API | Host header allow-list (421), SameSite=Strict cookie, Origin check, per-session CSRF header, JSON-only bodies, no CORS | — |
| Credential guessing | 160-bit random passphrase, scrypt (N=2^15), lockout with exponential backoff; optional passkeys (WebAuthn ES256, user verification required) that can replace the passphrase for sign-in | In-memory throttle resets on restart; passkey code is custom and awaits independent review |
| Session theft | HttpOnly+SameSite=Strict, 12h expiry, hashed token at rest, `Secure` when non-loopback | Device list/revocation UI |
| High-risk approval by stolen session | Step-up passphrase (5 min window) for high-risk approvals | Hardware key step-up |
| Approval tampering / replay / double execution | Canonical-JSON digest, digest echoed by client and re-verified at execute, status transition as lock, expiry, pause blocks execution | Tested |
| Voice/phone spoofing ("yes", caller ID) | Phone/SMS channels rejected outright; chat can never approve | Verified-identity step-up design needed before enabling |
| SSRF via research fetch | https-only, per-host approval, allow-list re-checked on every redirect, DNS result must be public, connection pinned to vetted IP, no creds in URL, size/time/redirect caps, text types only | Proxy-aware egress policy if deployed behind one |
| Prompt injection in fetched content | Content is data: quoted, flagged, no instruction path; tools/permissions are server-side; injected "add to allow-list" produced no approval/state change (test) | Re-test with each new tool/model |
| XSS from untrusted documents | Documents rendered as React text nodes only (no `dangerouslySetInnerHTML`); CSP `script-src 'self'`, `frame-ancestors 'none'` | — |
| Provider API key theft/leak | Key only in env var or `data/secrets.json` (0600); set via hidden-input CLI; no API route returns it (canary test over `/api/*`); used only server-side by the SDK; audit redacts key-shaped strings | Any process running as you can read the file; Keychain storage is a later hardening |
| Model output used to act (prompt injection via chat/memory/documents) | Model gets **no tools** and its output is rendered as text; fixed rules precede persona; memories and pasted text are labelled `<data>` with angle brackets stripped; commands and approvals are separate server-side paths | Re-review before ever giving the model tools |
| Persona/preferences used to weaken rules | Persona is a strict schema, sent after the fixed rules, as "style only" | — |
| Content sent to a model provider | Private mode keeps the model off by default; opt-in toggle is audited; memories/history are not sent in private mode | **Provider retention terms are unverified**: review Anthropic's before adding a key |
| Runaway model spend | Reserve-before-call, daily ceiling ($1 default; raise = high-risk approval), 90%/100% monthly gates, usage table | Provider-side spend limit in the Anthropic console (do this when creating the key) |
| Secrets in logs/memory | Audit redacts secret-shaped strings; memory refuses secrets; server logs error messages only, never bodies | Pattern-based, not perfect |
| Tampering with history | Hash-chained audit log, verified on the Activity page and in backup verification | Chain protects against edits by casual tampering, not an attacker with DB write + recompute; anchor head hash off-box later |
| Runaway spend | Reserve-before-dispatch, 75/90/cap gates, fixed costs first, cap changes need high-risk approval | Provider-side limits when providers exist |
| Dependency compromise | 4 runtime deps pinned exactly; `npm audit` clean at install; no install scripts needed | Add lockfile review + update cadence (DEPENDENCIES.md) |
| Private-mode leakage | Server creates no message/audit/memory/task rows in private mode (test) | Provider-side retention must be documented per provider before one is added |
| Data at rest | DB file `0600`, data dir `0700` | Disk encryption relies on the OS (FileVault); encrypted backups built (public-key, `npm run backup`); off-site copy job still manual |
| Standing permission abused (prompt injection making the model propose something that then auto-runs) | Only 4 low-impact, undoable kinds can be granted; daily cap; expiry; per-interface; paused = off; granted only with step-up on the dashboard; uses counted and audited | An injected suggestion could still add a few junk tasks or tick a habit within the cap; all are visible and undoable. Residual risk accepted by choosing to grant |
| Weather feed used to inject instructions or reach internal hosts | Two fixed hosts, https only, public-IP pinned, no redirects, 200 KB cap; response parsed against a strict numeric schema; the model only sees text we build from numbers and a fixed word table; place names cleaned | If Open-Meteo itself were compromised it could report false weather; labelled with its source and age |
| Web pages (via web search) used to inject instructions or to steal private data | Off by default; explicit "search:" only; search turns carry no calendar/tasks/memories/history and cannot create proposals or actions; web fetch tool not enabled (no arbitrary URL for exfiltration); search runs on Anthropic's servers (our server never connects to pages); output cleaned, https-only sources, labelled unverified; stored flagged and later shown clipped; per-question and daily caps | A page can still make the answer wrong or misleading, or make the model search for something odd (costs a cent; no private data is in the prompt to leak). Luke should verify anything important via the sources |
| Knowledge graph/decision log leaks or keeps what Luke wanted gone (excluded names, secrets, stale links; poisoned import file; a model's challenge treated as fact) | Exclusions enforced at every write path (memory, suggestions, graph, decisions, import) and removed from existing graph records; pattern not audited; derivation is deterministic with no model; forgetting cascades to links/edges (and optionally memories) and suppresses re-derivation; export skips secrets/excluded; import is strict-schema, checksummed, additive, step-up gated and skips secrets/excluded; retention is opt-in, previewed, step-up gated, audited, and never touches memories/graph/decisions; challenge is on demand, sends only decision text fenced, JSON-validated, labelled as opinion; read-only lookup unavailable in private mode and SMS | Backups made before a forget still contain it until they roll off; a name written differently (nickname) is not caught by an exclusion; guessed links can be wrong (shown dashed with confidence) |
| Model router/evaluations used to leak private text to an unvetted vendor, or to run up spend | Providers need code in Jarvis plus your explicit approval; separate flag for private text; private-capable jobs only route to providers allowed it, re-checked at every use (withdrawal takes effect immediately); evaluation uses fixed synthetic cases only (a test asserts no personal terms), runs only on your step-up, shows worst-case cost, has its own cap inside the monthly/daily caps, one run at a time; route and approval changes need step-up and are audited; no automatic switching | A vendor you approve for private text sees that text under its own retention terms (review before approving); score thresholds say little about quality outside the fixed questions |
| Integrations used as a way in: poisoned ChatGPT export, a brief that leaks secrets or tells an agent to push to main, or imported chats leaking into answers | No live connection to either service (files and text you hand over / copy yourself); import is strict-schema, size-capped, parsed in your browser, secrets and excluded names removed on the way in, private by default and never given to a model, memory, graph or answers unless you click per chat; text shown only as text; briefs refuse secrets and excluded names, the safety rules are fixed in code (model output cannot remove them), edits revert to draft, and Jarvis never launches anything | Anything you paste into a brief is copied by you into another tool under that tool's rules; an import you mark searchable exposes its title in chat answers |
| Self-improvement turns into self-modification: a model-proposed workflow that escalates, exfiltrates or runs away; an untested change going live; a bad rollout staying on | Models can only propose a chain of existing skills (same validator as any workflow: permissions are the union, tier the highest, web output cannot feed side-effect steps) or words for a human to build; no code is written or installed by Jarvis; every candidate is tested in a throwaway in-memory database with made-up data (11 checks including hostile inputs, permission refusal for unknown agents, protected tables untouched, no snowballing, no regression in active workflows, no model spend); only Luke switches anything on, with step-up, after the checks re-run; rollouts are watched and auto-disabled (restoring the previously approved workflow); drafting by itself is off by default, weekly, capped and draft-only; drafts cost at most $1 each inside the monthly cap | The sandbox cannot prove a workflow is useful, only that it is safe on made-up data; real data may behave differently, hence the watch period; gap detection only sees failures that are logged |
| Calendar writing damages or leaks your calendar (wrong event, injection in a title, repeating series, an unapproved write) | Every write is a high-risk approval bound to the exact title, time and calendar (passphrase or passkey each time); the event is passed to macOS as JSON data, never spliced into the script; repeating and all-day events are never moved; only the calendar you chose is written; paused Jarvis writes nothing; failures are recorded and capped at three tries | A real Apple Calendar run has not been verified yet; an approved event is still written to a calendar that may sync to other devices |
| Agent Foundry builds an agent that overreaches, is tricked, or is switched on without you | It can only design research agents on public information (no private data, no actions); skills limited to public read-only ones; simulation includes a tricked and an out-of-scope request and a failing guard blocks approval; plain-rule audit plus duplicate check; approval needs a fresh step-up; runs under the shared self-started limits and the exploring budget; pause, retire and Stop everything switch it off | Simulations are made-up situations, not real-world proof; the second opinion is a model's view |
| Delegation sends work to an agent that does not exist, or loops on spending | Only agents that really exist are chosen; unconnected ones are named and refused; spending limit per job (default $3, max $10); weak work is sent back at most twice; you can cancel at any time | The quality tests are simple (found something, confirmed by a second site, finished) |

## Retention note (forget/backups)
`forget` deletes the memory row. Prior snapshots made with **Create local snapshot** still contain it until deleted by you. Policy: keep the 7 most recent snapshots; delete older ones; off-box copies must be encrypted and age out on the same schedule. (Automated pruning is not built yet.)

## Explicitly out of scope today
Screen observation, Mac companion, telephony, third-party OAuth connections — none exist, so none of their threats are mitigated yet; each needs its own model before building.

| Direct mode (calendar) | A bad actor makes Jarvis change the calendar without Luke | Only Luke's own typed chat message or an authenticated page call can trigger it; web, imported-chat and agent text cannot; devices (car/watch) cannot; pause and emergency stop block it; audited; switch-off needs a step-up | Prompt-injection into a typed message is not possible; a stolen unlocked session could edit events (accepted by Luke) |

| Open and show (opener) | A web page, imported chat or agent makes Jarvis open a malicious page or send a message | Only Luke's typed message can ask; https public pages only; an address not in his words is never opened directly; pages from search are opened only on his request; fixed app list; drafts are never sent, only opened for him; rate limit; pause; audit (host only) | Opening a page is like clicking a search result; a hostile result page could still load in his browser (he chose this) |

| Jarvis Browser (looks around and clicks) | A page tells the AI to do something harmful (prompt injection), or a disguised button does damage | The model only picks numbered items from a list built and filtered in code (risky words and other-site links removed); no typing or form submission; PUT/DELETE/PATCH, cross-site posts, leaving the site, downloads, pop-ups and dialogs are refused by the browser itself; sensitive sites refused; page text fenced as untrusted; step, money and time caps; Stop and Stop everything; separate profile; summary only is stored | An innocent-looking button that performs a same-site POST; page text is sent to Claude (privacy); saved logins sit in data/browser-profile (deleted by Forget logins) |
